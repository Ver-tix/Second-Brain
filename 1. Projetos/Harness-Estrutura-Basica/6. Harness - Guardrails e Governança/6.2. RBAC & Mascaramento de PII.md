## Controle de Acesso Basado em Funções (RBAC - Role-Based Access Controle) e Mascaramento/Anonimização de Dados (Data Masking)
### As 3 Camadas de Proteção de Dados Sensíveis

Para garantir que o agente processe pedidos sem vazar dados sigilosos, a governança aplica um fluxo em três etapas:

```
[Usuário+Credencial]──►[1.Checagem de RBAC]──►[2.Anonimização/Masking] 
                                                                 |
                                                [3.Agente(LLM)]◄─┘										               		                       │
		                                               ▼
                                         [Resposta Sem Dados Sensíveis] 
```

#### 1. Autenticação e Controle de Acesso (RBAC no Tool Calling)

O agente herda o **nível de permissão (token JWT/API Key)** do usuário que está logado na sessão:

- **Operador de Suporte Nível 1:** A ferramenta de busca de clientes retorna apenas o status do pedido. O campo `credit_card` vem nulo ou omitido direto do banco de dados.
    
- **Gerente de Fraudes (Com Credencial Elevada):** A ferramenta retorna o dado completo, pois a credencial do usuário logado permite esse acesso.
    

#### 2. Anonimização e Mascaramento Dinâmico (PII Redaction)

Antes que o dado lido do banco chegue ao contexto da LLM, um **filtro de sanitização em código** substitui informações sensíveis por marcadores anônimos:

- **Dado Bruto do Banco de Dados:**
    ```JSON
    { "cliente": "João Silva", "cpf": "123.456.789-00", "cartao": "4532.XXXX.XXXX.8891" }
    ```
    
- **Dado Sanitizado Enviado para o Agente:**
    ```JSON
    { "cliente": "João Silva", "cpf": "[MASCARADO_LEI_LGPD]", "cartao": "Final 8891" }
    ```

Dessa forma, mesmo que a LLM queira ou seja enganada para exibir o número do cartão, ela **fisicamente não possui essa informação em sua memória de contexto**.

#### 3. Guardrails de Saída (Output Guardrails)

Caso algum dado sensível passe despercebido pelo banco e chegue ao texto gerado pela LLM, um filtro de inspeção final (usando Expressões Regulares / Regex ou classificadores dedicados) analisa a resposta **antes de exibi-la na tela do usuário**:

> **Ação do Guardrail:** Se o texto da resposta contiver um padrão correspondente a CPF (`\d{3}\.\d{3}\.\d{3}-\d{2}`) ou cartão de crédito, o sistema substitui o valor por `[DADO_PROTEGIDO]` antes do envio.

## Quadro Geral da Governança de Agentes

Com isso, fechamos os quatro pilares da governança de IA:

|**Ameaça**|**Técnica de Defesa**|**Onde Atua**|
|---|---|---|
|**Jailbreak (Ataque Direto)**|Constituição no Prompt + Input Guardrails|Entrada do Usuário|
|**Injeção Indireta (Dados Externos)**|Delimitação de Tags (`<DATA>`) + Dual-LLM|Leitura de Ferramentas|
|**Ações Não Autorizadas**|Confirmação Humana (HITL) + Sandbox|Execução de Ferramentas|
|**Vazamento de PII / Dados**|RBAC nas APIs + Mascaramento de Dados|Retorno de Dados e Saída|
