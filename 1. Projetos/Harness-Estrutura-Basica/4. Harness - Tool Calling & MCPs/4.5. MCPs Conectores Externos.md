# MCP (Model Context Protocol): Conectores Externos

## Tool Calling genérico vs. MCP

As notas [[2.1. O Problema Que o Tool Calling Resolve]] até [[2.1.3. Defense in Depth (Defesa em Profundidade)]] descrevem o **mecanismo geral** de chamada de ferramentas: o agente gera um JSON, seu código executa a ação de verdade.

O MCP é uma **padronização** desse mecanismo, criada para resolver um problema específico: sem um protocolo comum, cada integração (Trello, Google Drive, Slack) exigiria um contrato JSON Schema próprio, escrito e mantido manualmente por cada desenvolvedor.

## Skills vs. MCP: a distinção que fecha o quebra-cabeça

||**Skill**|**MCP**|
|---|---|---|
|**O que oferece**|Conhecimento processual — _como_ fazer bem algo|Acesso externo real — capacidade _nova_|
|**O agente já sabia fazer sozinho?**|Sim, a skill só ensina o método certo|Não — sem o conector, a ação é fisicamente impossível|
|**Analogia**|Treinamento de um funcionário|Senha de acesso a um sistema|
|**Onde vive**|Arquivo `SKILL.md`, carregado sob demanda|Servidor externo, conectado via protocolo|

## Como funciona na prática

```
[ Agente decide usar uma ferramenta ]
        │
        ▼
[ Servidor MCP (ex: mcp.trello.com) ]
        │
        ├── Expõe uma lista de "tools" com JSON Schema (ver 2.1.1)
        ├── Recebe a chamada do agente
        ├── Executa a ação no sistema real (criar card, ler e-mail)
        └── Retorna o resultado formatado (ver 2.1.2)
        │
        ▼
[ Resultado injetado no Contexto de Runtime ]
```

## Por que MCP é Harness, não Cérebro

Um modelo sem nenhum MCP conectado continua sendo o mesmo LLM — os pesos não mudam. O que muda é só a "extensão do corpo": quantos sistemas externos o Harness consegue alcançar em nome do agente. É por isso que trocar de modelo não quebra suas integrações MCP, mas desconectar um MCP tira uma capacidade inteira do agente, independente de qual modelo esteja rodando.

## Segurança: por que MCP herda os mesmos riscos do Tool Calling

Cada conector MCP é uma nova superfície de ataque potencial — vale aplicar as mesmas camadas de [[2.1.3. Defense in Depth (Defesa em Profundidade)]]: validação de schema, princípio do menor privilégio (credenciais escopadas por conector) e HITL para ações de alto risco.
