Quando uma ferramenta falha (seja por um erro de conexão `404`, parâmetros incorretos ou retorno com dados vazios/corrompidos), o comportamento padrão de uma LLM sem arquitetura de agente é parar ou alucinar uma resposta.

Para que o agente continue funcionando de forma resiliente, utilizamos padrões de **Auto-Correção (_Self-Correction_)** e **Replanejamento (_Re-planning_)**.
## O Ciclo da Resiliência: Observação, Diagnóstico e Ajuste

Em vez de enviar a resposta final ao usuário imediatamente após a chamada de uma ferramenta, o ciclo de execução do agente passa por quatro fases:

```text
[ 1. Ação ] ──► Chamada da Ferramenta (Ex: API de Pesquisa)
                     │
                     ▼
[ 2. Observação ] ──► Captura do Retorno (Ex: Erro 404 / Lista Vazia)
                     │
                     ▼
[ 3. Diagnóstico ] ──► O agente analisa: "O que deu errado?"
                     │
                     ▼
[ 4. Decisão ] ──► Tentativa de Ajuste / Replanejamento / Fallback
```

## 1. Padrões de Auto-Correção (_Self-Correction_)

A auto-correção ocorre quando a falha é **local** (na própria chamada da ferramenta) e pode ser corrigida ajustando como a ferramenta foi invocada.

### A. Validação de Sintaxe e Parâmetros (Retry Loop)
Se o agente passa um parâmetro no formato errado (por exemplo, um texto onde a API esperava um número inteiro ou uma data no formato `DD/MM/AAAA` em vez de `YYYY-MM-DD`):
1. O sistema de execução da ferramenta captura a exceção em código e devolve a mensagem de erro exata como **Observação** para o agente:  
    
    > _"Erro de API: O parâmetro 'date' deve seguir a norma ISO-8601 (YYYY-MM-DD)."_   
    
2. O agente lê a mensagem de erro via _Chain-of-Thought_ (CoT):
    
    > _"Pensamento: Tentei passar a data como '14/08/2026'. Preciso corrigir a formatação para '2026-08-14' e tentar novamente."_  
    
3. O agente executa a mesma ferramenta com os parâmetros corrigidos.

### B. Refinamento de Query / Paráfrase

Se a ferramenta de busca não retorna nenhum resultado relevante (retorno vazio):

- O agente percebe que a busca foi específica demais ou utilizou termos inadequados.
- Ele gera uma nova query com sinônimos, termos mais amplos ou em outro idioma para realizar uma segunda tentativa.

## 2. Padrões de Replanejamento (_Re-planning_)

O replanejamento ocorre quando a falha é **estrutural** (a ferramenta está fora do ar, indisponível ou o caminho escolhido originalmente se provou inviável).

**1.Identificação do Bloqueio:**A ferramenta principal falhou de forma irrecuperável.
- O agente constata que a rota atual não trará resultados (ex: _"API de cotações em tempo real fora do ar"_).

**2.Preservação do Estado (Checkpointing):**Evita gastar tokens recomeçando do zero.
- O histórico de execuções bem-sucedidas das Etapas 1 e 2 é salvo no contexto. Apenas o plano a partir da Etapa 3 em diante será descartado  

**3.Invocação do Módulo de Replanejamento:**O agente reavalia os recursos disponíveis.
- Com base nas ferramentas sobressalentes descritas em seu contexto, o agente busca um caminho alternativo para atingir o mesmo objetivo.

  

**4.Execução da Rota de Alternativa (Fallback):**Substituição da ferramenta ou da abordagem.
- Em vez de usar a API original, o agente decide usar um raspador web (Web Scraper) ou consultar uma base RAG interna com dados consolidados.
## 3. Estruturação do Prompt de Controle de Erros
Para habilitar essa capacidade, o prompt do sistema (_System Prompt_) do agente orquestrador deve ter regras de decisão bem definidas.

```Markdown
### DIRETRIZES DE TRATAMENTO DE ERROS E REPLANEJAMENTO
1. A cada chamada de ferramenta, analise o bloco [OBSERVAÇÃO].
2. Se o retorno indicar um erro de parâmetros:
   - Identifique a causa do erro.
   - Limite máximo de tentativas de correção direta: 3 vezes.
3. Se a ferramenta retornar erro de servidor (5xx) ou indisponibilidade:
   - NÃO tente a mesma ferramenta novamente.
   - Ative o modo de REPLANEJAMENTO.
   - Crie um novo plano usando ferramentas alternativas de sua lista.
4. Se nenhuma ferramenta puder resolver o problema:
   - Interrompa a execução com segurança.
   - Esclareça ao usuário qual etapa falhou, por que falhou e o que foi tentado.
```

## Resumo dos Padrões

|**Tipo de Falha**|**Diagnóstico**|**Estratégia de Solução**|**Exemplo**|
|---|---|---|---|
|**Erro de Sintaxe / Formato**|Parâmetros mal formatados|**Auto-Correção Local**|Corrigir JSON ou formato de data e tentar de novo|
|**Retorno Vazio / Fraco**|Busca muito restrita|**Refinamento de Query**|Usar termos mais abrangentes ou sinônimos|
|**Ferramenta Indisponível (5xx)**|Erro no servidor externo|**Replanejamento (Fallback)**|Trocar a ferramenta X pela ferramenta Y|
|**Falha Irrecuperável**|Nenhuma alternativa viável|**Graceful Degradation**|Informar o usuário com transparência sobre o bloqueio|
