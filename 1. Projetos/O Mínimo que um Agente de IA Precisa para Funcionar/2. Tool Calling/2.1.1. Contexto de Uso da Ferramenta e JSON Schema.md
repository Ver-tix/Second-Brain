## Anatomia do Contrato de uma Ferramenta (Tool Definition)

Para que a LLM entenda e execute a ferramenta perfeitamente, fornecemos a ela um "contrato" dividido em três partes principais:

### 1. Assinatura e Propósito (`name` e `description`)

É aqui que entra exatamente o que você descreveu: o contexto, os casos de uso e os **limites** de atuação da ferramenta.

### 2. Esquema de Parâmetros (`parameters`)

Especifica quais dados o agente precisa extrair da mensagem do usuário para preencher a chamada.

### 3. Obrigatoriedade (`required`)

Define quais parâmetros são estritamente necessários e quais são opcionais.

## Exemplo Prático em JSON Schema

Imagine a ferramenta de previsão do tempo que mencionamos:

```JSON
{
  "type": "function",
  "function": {
    "name": "get_weather_forecast",
    "description": "Obtém a previsão do tempo atual ou futura para uma localização específica. USE QUANDO o usuário perguntar diretamente sobre o clima, temperatura, chuva ou condições do tempo. NÃO USE se a pergunta for sobre fatos históricos gerais, definições de clima ou se o usuário não especificar nem puder inferir um local.",
    "parameters": {
      "type": "object",
      "properties": {
        "location": {
          "type": "string",
          "description": "Nome da cidade e país/estado. Exemplo: 'Fortaleza, CE' ou 'Paris, França'."
        },
        "days": {
          "type": "integer",
          "description": "Número de dias para a previsão (de 1 a 7). O padrão é 1 (clima atual)."
        },
        "unit": {
          "type": "string",
          "enum": ["celsius", "fahrenheit"],
          "description": "Unidade de medida de temperatura. Padrão: 'celsius'."
        }
      },
      "required": ["location"]
    }
  }
}
```

## Por que os "Casos Negativos" (`NÃO USE`) são cruciais?

Sem a restrição do "quando não usar", acontecem dois erros clássicos de arquitetura:

1. **Invocação Desnecessária (Custo de Latência e API):**
    - **Usuário:** _"O que é o fenômeno El Niño?"_
    - **Agente sem restrição:** Executa `get_weather_forecast(location="El Niño")` $\rightarrow$ A API falha ou retorna dados inúteis.
    - **Agente com restrição:** Percebe que é uma dúvida conceitual/histórica e responde direto da própria memória.
        
2. **Ambiguidade entre Múltiplas Ferramentas:**
    - Se você tem a ferramenta `search_database` (busca interna) e `search_web` (busca no Google), o "NÃO USE" em cada uma é o que impede o agente de entrar em dúvida e chamar as duas ao mesmo tempo.

### O Próximo Ponto Crítico do Tool Calling

Assim que o agente lê o contrato e decide gerar a chamada, ele retorna o seguinte JSON no seu fluxo de resposta:

```JSON
{
  "tool_calls": [
    {
      "name": "get_weather_forecast",
      "arguments": { "location": "Fortaleza, CE", "unit": "celsius" }
    }
  ]
}
```

O seu sistema em Python captura essa chamada, executa o código da API de tempo e recebe o retorno bruto da API (ex: `{"temp": 30, "condition": "sunny", "humidity": 75}`).
