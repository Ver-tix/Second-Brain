>[! Um Rápido Spoiler:]
>**Tool Calling** (ou _Function Calling_) é o que transforma uma IA de um mero "gerador de texto" em um **Agente capaz de agir no mundo**.
>
>Sem ferramentas, o agente é apenas um consultor teórico. Com ferramentas, ele consulta bancos de dados, envia e-mails, cria chamadas de API, roda código e executa tarefas.

>[! ]
>### O Problema Fundamental do Tool Calling
>LLMs **não executam código diretamente**. O modelo de linguagem é apenas uma calculadora estatística que prevê o próximo token de texto.
>
>Então, quando dizemos que o agente "chama uma ferramenta", como isso funciona na prática?
>
>A IA não clica num botão; ela **gera um texto num formato muito específico** (geralmente JSON) dizendo: _"Eu quero rodar a função X com os parâmetros Y e Z"_.
>
>O nosso código ou a nossa plataforma No-Code é quem lê esse JSON, executa a ação de verdade no mundo real e devolve o resultado para a IA.

# Vamos Iniciar

## Imagina a seguinte situação:

Você quer dar ao seu agente a capacidade de **consultar a previsão do tempo**.

Para fazer isso, você precisa explicar para a IA qual ferramenta existe e como usá-la.

Se você simplesmente disser no prompt: _"Você tem uma ferramenta de tempo, use-a quando o usuário perguntar"_, a IA frequentemente vai errar a cidade, passar datas no formato errado ou tentar invocar funções que não existem.

**Que tipo de informações mínimas e precisas você acha que precisamos passar para a IA na "documentação" dessa ferramenta para que ela saiba exatamente QUANDO e COMO usá-la sem errar?**

> Contexto e casos de uso (um "quando usar" e "quando não usar")

Você acertou na mosca! Definir o **quando usar** e **quando NÃO usar** é exatamente o divisor de águas entre um agente que aciona ferramentas de forma precisa e um agente "gastador" que chama APIs sem necessidade.

Além do contexto de uso, o protocolo padrão da indústria (adotado pela OpenAI, Anthropic, Google, etc.) exige uma estrutura técnica rígida em **JSON Schema**.
#### Para saber mais sobre a **anatomia do Contrato de uma Ferramenta,** clique no link a seguir [[2.1.1. Contexto de Uso da Ferramenta e JSON Schema]]

## No link acima, vimos que a ferramenta vem em um schema em sintaxe JSON, e retorna também uma sintaxe JSON

**Como você acha que devemos devolver esse resultado bruto da API para o agente, de forma a garantir que ele interprete os dados corretamente sem gastar tokens excessivos?**

> Formatando a resposta, obviamente

Na mosca! 

Formatar o retorno de uma ferramenta (a mensagem com a função `tool` ou `function`) é um dos maiores pontos de otimização de custo e latência em sistemas de agentes.

Se a API externa devolve um JSON bruto com 50 campos inúteis (como metadados de servidor, IDs internos ou links de rastreio), enviar tudo isso direto para o contexto do agente causa três problemas:
1. **Desperdício de Tokens:** Você paga por tokens que a LLM nem vai ler.
2. **Poluição da Janela de Contexto (_Context Stuffing_):** Informações irrelevantes poluem a atenção do modelo (_attention mechanism_), aumentando o risco de alucinação ou perda de foco na instrução original.
3. **Aumento de Latência:** Quanto maior o prompt retornado, mais tempo a IA leva para processar a resposta.

## Próxima Fronteira no Tool Calling

Sabendo como estruturar o **Contrato (Tool Definition)** e como limpar o **Retorno (Tool Response)**, a pergunta de segurança crucial é:

**Como evitar que o agente execute chamadas perigosas ou indesejadas quando os dados de entrada vêm de fontes não confiáveis (ex: salvar no banco com parâmetros nocivos ou rodar comandos inesperados)?**

> Utilizamos mecanismos de padrão de segurança para sanitizar, validar e isolar (sandbox) a execução de ferramentas em agentes

Exatamente! Quando damos a um agente a capacidade de invocar código, consultar bancos de dados ou acionar APIs, estamos abrindo a nossa infraestrutura para entradas de dados geradas por uma IA.

Isso expõe o sistema a dois vetores principais de ataque/falha:
1. **Injeção de Prompt Indireta (_Indirect Prompt Injection_):** Um dado vindo de fora (como um e-mail ou documento lido pela IA) contém um comando malicioso que engana a LLM para invocar ferramentas perigosas.
2. **Alucinação de Parâmetros / _Hallucinated Payload_:** O agente tenta rodar parâmetros inválidos, malformatados ou acidentalmente destrutivos (como `DELETE * FROM users`).

Para blindar a arquitetura, aplicamos o princípio da **Defesa em Profundidade (_Defense in Depth_)** em três camadas: **Validação**, **Permissões** e **Isolamento**.
